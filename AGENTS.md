# AGENTS.md

AccountManager («Konto»): central account portal for own services. Users log in through an OpenID Connect provider (Pocket ID), see their services, register per service, and admins manage services and access. Concept, decisions and phases: `docs/KONZEPT.md` (German). Phase 4 (MVP), the households (phase 8), the entitlements (phase 6a) and the invoices (phase 6b), each on the AccountManager side, are implemented.

## Stack

- Laravel 13, PHP 8.4, MariaDB 10.11, DDEV (`accountmanager.ddev.site`). Run PHP/Composer/Artisan/npm via `ddev`.
- Filament 5 admin panel at `/admin` (`AdminPanelProvider`, only `users.is_admin`). The user facing part is plain Blade + Tailwind 4 (`resources/views`, layout `<x-layout>`) in the look of Chorelist/Shoppinglist: logged in an app bar with tabs (portal, households, profile; admins also get an «Admin» link to the panel in a new tab, same `canAccessPanel()` check), guests a centred column with the icon; component classes (`button`, `button-secondary`, `field`, `label`, `tab`, `notice`, `rows`, `badge`) and the dark mode (follows the device, palette swap) in `resources/css/app.css`, accent `--color-brand` (red). Laravel's error pages use `errors/minimal.blade.php`.
- Laravel Socialite + `kovah/laravel-socialite-oidc` for the login, `dompdf/dompdf` + `sprain/swiss-qr-bill` for the invoices, Larastan level 7.
- Icon: the Narrenhaus logo (both jesters, traced from the original PNG): `src/logo.svg` (also `public/narrenhaus.svg`), rendered to `src/favicon.png` (1024 px, transparent) → `ddev npm run favicon -- --source src/favicon.png --theme '#b91c1c' --bg '#fafaf9' --padding-bg '#fff4cc' --clean` (`partials/favicon.blade.php`, also in the panel via `HEAD_END`). Highlight color red (buttons, panel `Color::Red`). Link previews: `partials/meta.blade.php` + `public/og-image.png`.
- Generic for other hosters: domains, provider, texts only through configuration. Default locale `de` (`lang/de.json`; regional locales like `de_CH` fall back to it in `AppServiceProvider`, keys are the English texts, Swiss spelling "ss", informal "du").

## Concepts

- `services`: catalog (`key` = registration slug, `type` oidc|external, `login_url` = SSO start of the app, `access_group` = group in the identity provider, optional `admin_group` for the app's admins, `self_signup`, `requires_approval`, `visible`, `position`).
- `service_accounts`: access of a user to a service, status `requested` | `active` | `suspended` (`App\Enums\AccountStatus`), `is_admin` (admin in the app). `App\Accounts\Access`: `claim()` (portal and registration: active right away with self-registration and without approval, otherwise requested and the admins get `AccessRequested`), `approve()` (mails `AccessGranted`), `suspend()`/`reactivate()` (through `App\Accounts\Suspensions`: never automatic, reason required in the panel, mails `Suspended`/`SuspensionLifted`, history in `suspensions`; the same for subscriptions). Suspended accounts stay suspended for the user.
- The AccountManager is the source of truth for access: `ServiceAccountObserver` queues `SyncUserGroups` on status changes (and `Entitlements::refresh()` queues it when entitlements change); it sets the user's groups in the provider to the `access_group`s of their active accounts plus the `admin_group` for admins and the `group`s of their effective features (`User::desiredGroups()` → `Entitlements::groups()`) and keeps all groups no service or feature manages (`Service::managedGroups()`). The OIDC clients in Pocket ID are restricted to their group, so a missing group blocks the login at the provider.
- Self-registration (`RegistrationController`, `App\Accounts\Registrar`): `/register` (account only, the services follow in the portal; needs `AUTH_SIGNUP_ENABLED` and a managed provider, linked on the login page) or `/register/{service}` (a service key must not be `sent`) (honeypot `website` + 3 s time trap with the encrypted render time, throttled, same answer for known and unknown addresses, no new mail to the same address within 5 minutes) → `registrations` row with the SHA-256 of the token, `ConfirmRegistration` mail (valid `Registration::LIFETIME_DAYS`) → `GET /confirm/{token}` only shows a button (mail scanners must not confirm) → `POST` creates or finds the local user and the provider identity (`oidc_sub` = Pocket ID user id), claims the service (if any), syncs the groups synchronously and lets Pocket ID mail a login code to new identities. An existing identity is linked and its address set as verified (the apps link accounts only by verified addresses). Failures at the provider roll back (the link can be used again). `registrations:prune` (daily).
- Portal (`/`): services with their status, claim access, "Open" leads to `services.login_url` (the SSO start of the app, so logging in links an existing account there by email) or `url`.
- Profile (`ProfileController`, `/profile`): name is saved in the provider right away; a new email address gets a signed link (`profile.email`, 24 h, bound to the old address via `from`, GET only shows a button) and is set in the provider as verified on confirmation. Links to the passkey page of the provider (`identity.account_url`, default `<issuer>/settings/account` with pocket-id). Users never need the provider's UI except for the login and the passkeys (Pocket ID: `ALLOW_OWN_ACCOUNT_EDIT=false`, `HOME_PAGE_URL` = the AccountManager).
- Login: `/login` (button) → `/auth/oidc/redirect|callback` (`OidcController`, `App\Auth\OidcLogin`: by `oidc_sub`, otherwise by an email the provider marks as verified; unknown users get a local account with `AUTH_OIDC_REGISTRATION`). `App\Auth\OidcProvider` checks `iss`, `aud`/`azp`, `exp`. Admins may also log in with a password at `/admin/login` (emergency access only; `php artisan accounts:make-admin <email> --password`). Same structure as RecipeManager, Shoppinglist and Chorelist. Button label `App\Auth\OidcLabel::get()` (same class in all apps): `AUTH_OIDC_LABEL`, otherwise the `appName` Pocket ID publishes at `<issuer>/api/application-configuration` (cached), otherwise "SSO".

- Households (`App\Households\Households`, same rules and names as the local households of RecipeManager/Chorelist): `households` (`uuid` route key, `version` incremented on every change), `household_members` (role `admin`|`member`, `App\Enums\HouseholdRole`), `household_invitations` (SHA-256 of the token, 14 days, bound to the invited verified address, always needs consent; the link `/invitations/{token}` only shows a button, guests get `url.intended` and log in or register). Last-admin protection (`LastHouseholdAdmin`, rows locked). Portal `/households` (`HouseholdController`, `HouseholdInvitationController`); the panel only has read-only overviews. Deleting a user (`User::deleting`) runs `Households::forget()`: longest member becomes admin, empty households are deleted.
- Webhooks to the apps (`App\Households\HouseholdEvents` → `webhook_deliveries` → `App\Jobs\DeliverWebhook`, 8 tries, signed by `App\Webhooks\WebhookSignature`): only to services with `webhook_url` and `secret` where an affected user has an account; payload = full household snapshot (uuid, name, version, members' `sub` + role), nothing else. Each change locks the household row first so versions and snapshots stay consistent.
- API for the apps (`routes/api.php`, `AuthenticateService`: HTTP Basic service key + service secret; `Service::rotateSecret()` in the panel, stored encrypted, shown once): households of a sub, one household, shares, import proposals (`household_imports`, resolved by an admin in the panel, `App\Households\HouseholdImports`). Contract: `docs/HOUSEHOLDS-API.md`; keep it in sync with any change. Public `GET /api/info` (`Api\InfoController`, no auth, `throttle:60,1`): only `name` (`APP_NAME`) and `households_url`, shown by the apps instead of «Konto»; never add secrets or user data.
- Entitlements (`App\Entitlements\Entitlements`, contract `docs/ENTITLEMENTS-API.md`, keep it in sync): `features` per service (`key` like `shoppinglist.ai`, unique per service, optional provider `group`), `plans` (per service or bundle with `service_id` null; price fields for the invoices) with `plan_features`, `subscriptions` assigned by admins (`active`|`suspended`|`ended`, `starts_at`, `ends_at`; scope `effective()`), direct `feature_grants`. Effective per user and service = features of effective subscriptions + grants, and `admin` = `is_admin`, both only while the account is `active`. Snapshot `{sub, service, status (active|requested|suspended|none), admin, features, version}`; `entitlement_states` keeps hash and version per user and service (row lock, version only grows on a real change, continues after a deleted account). Observers (`ServiceAccountObserver`, `EntitlementSourceObserver` on subscriptions and grants, `FeatureObserver`, `ServiceObserver`, `EditPlan::afterSave`) call `refresh()`; a changed snapshot sends `entitlements.changed` to that service only. Users without `oidc_sub` are skipped (linking one sends the first snapshot). `User::deleting` sends `user.deleted` (only the sub) to every service where the user has or had an account, after `Households::forget()`. API `GET /api/entitlements/{sub}` (recomputes first; `404` for unknown users and users without an account at the calling service). `entitlements:refresh` (every 15 minutes): ends expired subscriptions, announces started ones (`--all` recomputes every linked user). Panel: plans, features (relation manager of services), subscriptions, grants and effective entitlements on the user page; the portal shows active plans and unlocked features.
- Invoices (phase 6b, `App\Billing`, KONZEPT 5.4): creditor and settings in `config/billing.php` (`BILLING_*`, placeholders in `.env.example`); `BillingConfig::enabled()` only with `BILLING_CREDITOR_IBAN`, `errors()` checks the creditor and that the reference type fits the IBAN (QRR only with a QR-IBAN, SCOR/NON with a normal IBAN; default from the IBAN). `billing:run` (daily 06:00, `Billing::run()`, cache lock; also «Run billing» in the panel): subscriptions of plans with `price_cents` > 0 and an `interval` are billed in advance per period (`BillingPeriod`: anchored at the start day, `addMonthsNoOverflow`, `once` = one period, no proration, periods starting before `ends_at`; `subscriptions.billed_periods` counts what is billed; the status does not matter, so suspended subscriptions keep being billed until an admin ends them) → one draft per user and currency (`invoices` + `invoice_lines`, number `<prefix><year>-0001` sequential per year, reference from year and sequence, recipient (`User::billingRecipient()`) and creditor as JSON snapshots) → PDF (`InvoicePdf`, dompdf A4, payment part laid out in `invoices/payment-part.blade.php` from `sprain/swiss-qr-bill` data, own page above 6 lines; stored on the `local` disk under `invoices/<year>/`, rendered again from the snapshots if missing) → status `open` + `InvoiceIssued` mail with the PDF. Unpaid invoices after `due_at` become `overdue` (`InvoicesOverdue` to `BILLING_ADMIN_EMAIL` or all admins), one `InvoiceReminder` `BILLING_REMINDER_DAYS` after the due date. Invoices are never deleted (10 years, model `deleting` throws; user deletion only nulls `user_id`): mark as paid (date, note) or cancel (reason) in the panel (`InvoiceResource`, `InvoiceActions`: PDF, resend, link to the user's suspend actions). Billing address `users.billing_*` (`BillingAddress` rules: structured QR-bill address, `QrBillText` characters) in the portal profile (only shown with billing or an address/invoices) and on the user page. Portal `/invoices` (own issued invoices, PDF download, 404 for others and drafts; tab only with billing or invoices). Not yet: camt.054 import (match payments by reference), VAT rates (only `BILLING_VAT_NOTE`), predefined suspension reasons.
- All webhooks go through `App\Webhooks\Webhooks::send()` (one event id and body for all given services, only services with URL and secret).
- `households:prune` (daily): old invitations and webhook deliveries (30 days).
- Easter egg: public `GET /easter-egg` (`easter-egg`, `EasterEggController`, no auth, nothing tracked): anti-piracy video (`public/easter-egg/narren-easter-egg.mp4` + `poster.jpg`, the only copy for all apps). "All rights reserved." in the mail footer (published `resources/views/vendor/mail/{html,text}/message.blade.php`, nothing else of the mail views) links to it via `App\Support\EasterEgg::url()`; the other apps link to `<ACCOUNT_MANAGER_URL>/easter-egg` only when that is configured.

## Identity provider

- `App\Identity\IdentityProvider` (find, list, create and update users, sync groups, send a login code), bound by `IDENTITY_DRIVER` (`config/identity.php`): `pocket-id` (`PocketIdProvider`, REST API with `X-API-KEY`: `POST /api/users`, `GET|PUT /api/users/{id}` (the PUT replaces the whole user, so unchanged fields are sent back), `GET /api/users/{id}/groups`, `PUT /api/users/{id}/user-groups`, `POST /api/user-groups` for missing groups, `POST /api/users/{id}/one-time-access-email`) or `manual` (reduced mode: nothing is created or synced, the admins get `ManualSetupNeeded`).
- Panel link to the provider's admin UI (dashboard card `PocketIdWidget` + navigation item, new tab; `App\Identity\AdminUrl`): only with `pocket-id`; `IDENTITY_ADMIN_URL`, otherwise `<origin of identity.account_url>/settings/admin/users` (`POCKET_ID_URL` may be internal, e.g. locally `http://ddev-AccountManager-pocket-id:1411`).
- Pocket ID needs SMTP and "Email login code from admin" for the login codes, and an API key of an admin (`POCKET_ID_API_KEY`).
- Commands: `accounts:import [--dry-run]` (links provider users by id/email and creates active accounts for the groups of services), `accounts:sync-groups`, `accounts:make-admin`.

## Deployment

- KeyHelp (PHP-FPM + cron), like the other apps. `.forgejo/workflows/deploy.yml` (same as RecipeManager): push to `main` → GitHub → Forgejo pull mirror → builds the assets in CI, uploads `public/build`, then `git pull` + `composer install --no-dev` + `migrate` + `optimize` on the server via SSH. Forgejo variables `SSH_HOST`, `SSH_USER`, `SSH_FINGERPRINT`, `DEPLOY_PATH`, `PRIMARY_SITE_URL`, secret `SSH_KEY`.
- Cron every minute: `schedule:run` and `queue:work --max-time=50` (mails, the group sync and the webhooks are queued; the schedule includes `entitlements:refresh` and `billing:run`).
- The invoice PDFs are in `storage/app/private/invoices` (kept 10 years): include `storage/app/private` in the backups; they can be rendered again from the database if lost.

## Local development

- Local Pocket ID: `.ddev/docker-compose.pocket-id.yaml` (`https://accountmanager.ddev.site:14111`, first start `/setup`, dev-only keys incl. API key `local-development-only-api-key`, Application Configuration via env with `UI_CONFIG_DISABLED=true`, mails to this project's Mailpit). Reach it at `http://ddev-AccountManager-pocket-id:1411`; the apps (RecipeManager, Shoppinglist, Chorelist) use the same URL as `AUTH_OIDC_ISSUER` through the shared `ddev_default` network. If the container exited (e.g. after sleep): `docker start ddev-AccountManager-pocket-id`. Put `AUTH_OIDC_*`, `IDENTITY_DRIVER=pocket-id`, `POCKET_ID_URL`, `POCKET_ID_API_KEY` into the git-ignored `.ddev/config.local.yaml` (`web_environment`). Mails of the AccountManager: its Mailpit (`ddev mailpit`); login codes are mailed by Pocket ID (also this Mailpit).
- Mails and the group sync are queued: `ddev artisan queue:work --stop-when-empty` (production: cron `schedule:run` + `queue:work --max-time=50` like the other apps).

## Rules

- Never store credentials in the repository; `.env` and `.ddev/config.local.yaml` are git-ignored.
- Only change groups the AccountManager manages (the `access_group`s of services); others belong to the admin.
- Registration and confirmation must not reveal whether an address is known.
- Apps get only household uuid, name and members' `oidc_sub` + role, and for entitlements only `sub`, service key, status, admin flag and feature keys of their own service (`user.deleted`: only the sub); never send other profile data, plans, prices, notes or suspension reasons in webhooks or API responses.
- Nothing is suspended automatically; suspending and lifting always mail the user.
- Invoices and their lines are never deleted or changed after issuing (only paid/cancelled/overdue fields); keep the snapshots so a PDF renders the same again.
